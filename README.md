# ClinicalPilot AI

Originally built for my MCA (Jul 2025 - Mar 2026); moved to GitHub and extended in 2026.

ClinicalPilot AI is a web-based clinical research suite for uploading datasets, identifying data-quality issues, analyzing cohorts, extracting study-paper insights, generating study reports, and chatting with research data.

## Architecture

React + TypeScript frontend, FastAPI backend, Pandas/NumPy/Scikit-Learn data processing, and PostgreSQL for persistence (SQLite for local development and tests).

The AI layer uses the Anthropic SDK (Claude) for streaming chat with tool calling and for paper summaries, local `fastembed` embeddings, and `pgvector` for retrieval.

## Local Development

```bash
npm install
npm run dev
```

The frontend runs at `http://127.0.0.1:5173`.

The API can run with:

```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload
```

### LLM credentials

Chat, paper analysis and the evals call Claude. Copy `backend/.env.example` to `backend/.env` and set `ANTHROPIC_API_KEY`. Without credentials those endpoints return HTTP 503 with a clear message; ingestion, profiling, cohort and report endpoints work without a key.

The first paper upload downloads the embedding model (`BAAI/bge-small-en-v1.5`, about 65 MB) into `backend/.model_cache`.

## Clinical data ingestion

| Endpoint | Input | What it does |
| --- | --- | --- |
| `POST /ingest/fhir` | FHIR R4 Bundle (JSON body) | Validates Patient, Condition and Observation resources with Pydantic and maps them into the `patients` table |
| `POST /ingest/cda` | C-CDA XML document (file upload) | Parses the document with lxml into the same patient model |
| `GET /patients` | | Lists ingested patients |

Invalid records do not stop an ingestion. They are stored in the `ingestion_rejects` table with the reason and the original payload, and returned in the response. Resource types that are not ingested (Encounter, Claim and so on) are counted under `skipped_resource_types`.

Mapping rules:

- Type 2 diabetes, hypertension and kidney disease flags come from SNOMED CT and ICD-10 codes (see `backend/app/mapping.py`). Resolved conditions are stored but do not set a flag.
- Blood pressure is the most recent reading (LOINC 85354-9 panel, or 8480-6 and 8462-4).
- Age is computed from the birth date, or the age at death for deceased patients.

Try it with the synthetic samples in `sample_data/`:

```bash
curl -X POST http://127.0.0.1:8000/ingest/fhir -H "Content-Type: application/json" --data-binary @sample_data/fhir_bundle_synthea_style.json
```

```bash
curl -X POST http://127.0.0.1:8000/ingest/cda -F "file=@sample_data/ccda_synthea_style.xml"
```

Both sample files are hand-written in the shape Synthea produces and contain no real patient data. Bundles and C-CDA files generated by [Synthea](https://github.com/synthetichealth/synthea) can be posted to the same endpoints.

## Paper analysis (RAG)

`POST /papers/analyze` accepts a `.pdf`, `.docx`, `.txt` or `.md` file. It splits the text into overlapping chunks, embeds them, and stores them in `paper_chunks` (a pgvector column on PostgreSQL). It then retrieves the best chunks for each summary field and asks Claude to summarize from those chunks only. The response includes the summary and the `sources` (chunk index, score and excerpt) it was built from.

`GET /papers/search?query=...` returns the top matching chunks without calling the LLM.

## Chat with tool calling and streaming

- `POST /chat` returns the complete answer as JSON.
- `POST /chat/stream` returns server-sent events: `token`, `tool_call`, `tool_result`, then `done` (or `error`). The assistant panel in the frontend renders the answer as it streams in.

Claude answers by calling three tools instead of computing numbers itself:

| Tool | Purpose |
| --- | --- |
| `discover_cohort(filters)` | Count and list the unique patients matching a set of filters |
| `dataset_stats(column)` | Column statistics or a dataset overview, optionally within a cohort |
| `search_papers(query)` | Semantic search over uploaded papers |

Each answer comes back with `sources` (the dataset or the paper chunks used) and the `tool_calls` that were made.

## Evaluation

`backend/evals/golden.json` holds 20 questions about the sample dataset with known answers.

```bash
python backend/evals/run_evals.py
```

This asks every question through the chat agent, scores the answers, prints a summary and writes `backend/evals/results.json`. An answer is correct when the value on its final `ANSWER:` line matches the expected value, and grounded when the agent made at least one successful tool call and cited a source. It needs Anthropic credentials.

```bash
python backend/evals/run_evals.py --check-golden
```

This verifies the 20 expected answers against the tools without calling the LLM.

## Tests

```bash
npm test
npm run backend:test
```

The backend tests mock the LLM and the embedding model, so they run in CI without an API key or a model download.

## Docker

```bash
docker compose up --build
```

The database service uses the `pgvector/pgvector:pg16` image. Set `ANTHROPIC_API_KEY` in your shell or in a root `.env` file before starting so the API container can reach Claude.

## Implemented Demo Modules

- Research dashboard with enrollment, disease distribution, missing-data, and activity views
- Dataset quality engine UI for missing values, duplicates, invalid entries, and health mapping
- AI data cleaning assistant panel with streaming, tool-calling chat
- Research paper analyzer with retrieval-augmented insight extraction and cited sources
- Cohort discovery and protocol eligibility checker
- Study report generator with AI-generated draft preview
- Digital twin research simulator for recruitment and staffing scenarios
- FastAPI endpoints for dataset profiling, FHIR and CDA ingestion, cohort discovery, protocol checks, paper analysis, and dataset chat
